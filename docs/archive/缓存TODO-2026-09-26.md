## 一、现状与总评

三类缓存机制(音频 / 封面 / 配置)已逐行核实(`ensureSpace`、下载流水线、
启动自愈、封面完整性检查)。**设计与实现整体质量高**:

- 双结构缓存:drift 索引 + 内容寻址文件;封面文件名 = `sha1(内容)` 天然去重,
  音频 v6 起 `contentHash` 并启动时 `deduplicateByContent()` 折叠重复文件;
- LRU 诚实:播放命中 `touch()`,封面 `lookup` 也 bump,`idx_audio_cache_lru`
  支撑驱逐;
- 两段式容量校验(音频预检 → 下载后按真实字节复核、超限删文件 + 异常;
  封面长度已知,单次精确校验);
- 启动自愈:音频与封面各跑 `checkIntegrity()`;
- 降级纪律:缓存失败只 log 不抛出,播放永不被打断;
- 限额即时生效:每次 `ensureSpace` 重读 `CacheSettings`,下调限额即 `enforceLimit()`。

**应用配置缓存**(SharedPreferences + provider 单例 + 内存广播流)机制简洁正确,
仅有两条低危备注(见 §四)。

## 三、改动方案

### 阶段 ① 补索引(高优先级,低风险,可立即做)——对应 P3

> **状态:已完成** —— 随 schema v10 落地(两表各补 `content_hash` / `file_path` 索引,
> 迁移 + 索引存在性测试),见 spec §6.3。

**改动面**:

| 表 | 新增索引 |
|---|---|
| `audio_cache` | `content_hash`;`file_path` |
| `cover_cache` | `content_hash`(若已有 url 唯一键则补);`file_path`;`last_accessed_at`(供封面 LRU 驱逐) |

建议把 `file_path` 相关查询与 `(pinned, last_accessed_at)` 现状核对后再定最终
组合,避免冗余索引。

**成本**:drift schema 改动 + 迁移。约 **≤0.5 小时**。**风险**:低。
**收益**:插入去重、驱逐循环从全扫/N+1 变为索引查找;万级行数时设置页与下载
不再卡顿。

### 阶段 ② 封面独立配额 + 收敛配额策略(中风险,挂起)——对应 P1 + P4

> **状态:已完成,但选型与下面的两个备选都不同** —— 2026-09-26 重构给出的答案是
> **按歌曲分配配额**,而不是"给封面一块独立硬配额":
>
> - **层 1 = 歌曲资产行**(`audio_cache` 加 `cover_path`):音频与随行封面作为**同一条记录
>   同生共死**,行级驱逐。已缓存歌曲的封面不再可能被音频饿死 → **P1 消失**。
> - **层 2 = 临时封面缓存**(`cover_cache` 收窄为"仅未缓存歌曲"):固定 256 MiB、
>   每次启动整体清空,不可配置(因此无需新增配额 UI)。
> - 两 store 各自单一所有者、各自只读自己的字节,**跨表协调器不复存在** → **P4 消失**。
>
> 代价见 spec §13:pinned/离线不占任何配额(上限不再约束总磁盘占用);未下载歌曲的
> 封面是会话级的,每次启动首屏会重新拉图。完整语义见 spec §3/§5/§7。

**前置决策项(未定,需产品意图确认)**:
> 封面是"牺牲一切保音乐下载"的一次性装饰,还是"值得保证一份驻留"的常驻资源?

- 维持现状(封面永远先驱逐):仅做阶段③的 P4 收敛即可。
- 封面独立配额(推荐备选):给封面一小块**独立硬配额**(如固定 64 MiB 或 N 张),
  封面驱逐只在封面配额内进行,音频配额独立;同时顺手把两份 `ensureSpace`
  合并为单一 `CacheQuota` 协调器(消掉 P4 的跨表读写与重复策略)。

**触发条件**(满足再执行):
1. 产品决策确定"封面需保证驻留";
2. 出现"封面反复重新下载"的实际用户反馈;
3. 进入 1.0 功能加固期。

**成本**:策略收敛约 1–2h;若加独立配额再加 1–2h。**风险**:中
(涉及两 store 的驱逐核心路径,现有测试应可全部覆盖)。

### 阶段 ③ 预检获得真实长度(低优先级,长期)——对应 P2

> **状态:仍然延期** —— 重构明确将其列为非目标(spec §2/§12);触发条件见下。

**前提**:`StreamInfo` 透出长度信息(需 `StreamResolver` API 层改动,影响
Bilibili 源实现与测试);或退而求其次增加"最大单曲字节"启发式阈值。

**触发条件**:用户反馈出现明显的超限下载白费带宽。

**成本**:API 改动跨 resolver/源适配器/测试,约 **1–2h**。**风险**:中。

## 四、应用配置缓存——备注(无动作项)

1. `watchCacheSettings` 仅广播进程内更新,桌面多窗口不同步(当前单窗口,无影响);
2. 读取失败静默回退 1 GiB 默认值,瞬时不可用时 `enforceLimit` 可能误驱逐到
   错误档位(如用户 2 GiB 被清到 1 GiB);下次读自愈。
   - **可选改进**(不动也可):失败时"保守不驱逐"。

## 五、明确不做

- 不引入独立缓存框架/内存缓存层,现有 SQLite + 文件结构足够。
- 不做多 window 跨进程设置同步,当前架构无此场景。
- P5 两项均视为已知行为,不修。
